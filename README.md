# E-commerce Fraud Detection

Business Analytics group project for detecting fraudulent e-commerce payment
transactions. The project starts from PaySim-style transaction data, enriches it
with contextual behavioural signals, trains fraud-risk models under class
imbalance, and exports a deployable scoring policy.

## Project Structure

```text
Module_01/   Business understanding, data dictionary, synthetic-data logic
Module_02/   Exploratory data analysis
Module_03/   Data cleaning
Module_04/   Feature engineering and train/test feature exports
Module_05/   Model development, validation selection, final test evaluation
Module_06/   Deployment demo: scorer, FastAPI service, Streamlit app
Module_07/   Monitoring and drift checks
Module_08/   Report tables and figures generated by the notebooks
models/      Persisted scaler, feature list, best model, and threshold policy
scripts/     Shared configuration and setup helpers
```

## Module 5 Modelling Protocol

Module 5 uses a behavioural-only modelling path. Mechanical PaySim balance
features are removed from the deployable model because they can encode simulator
leakage rather than reusable fraud behaviour.

The split protocol is:

```text
80% historical train / 20% untouched future test
inside the 80% train: 85% inner-train / 15% validation
```

Model family, balancing strategy, hyperparameters, and threshold are selected on
validation only. The final test set is evaluated once with the frozen validation
choice.

Balancing strategies compared in Module 5:

```text
original
class_weighted
SMOTE
undersampling
```

The current selected candidate is:

```text
behavioural features + undersampling + LightGBM
threshold = 0.0025, selected on validation
```

## Final Test Snapshot

Using the locked behavioural model on the untouched test set:

```text
test rows           552,504
actual fraud        4,258 (0.77%)
fraud caught        4,211
fraud missed        47
recall              98.90%
precision           5.15%
review queue        81,773 rows (14.80%)
```

The model is best interpreted as a risk-ranking and manual-review prioritisation
tool. It should not be treated as a fully automatic blocking policy without
additional cost calibration, capacity constraints, and shadow-mode validation.

## Notes

- Test data is never resampled or augmented.
- SMOTE and undersampling are applied only to training folds.
- `C_FP = 10` in Module 5 is an explicit review/friction-cost assumption, not a
  measured business constant.
- Module 7 provides monitoring outputs for drift and rolling performance checks.
